# Translations

How TicketFlow is translated, what GLPI actually does at runtime, and how to add a language.

---

## What ships

| Catalogue | Coverage |
|---|---|
| `locales/en_GB.po` / `.mo` | 211/211 — the source language, shipped explicitly |
| `locales/fr_FR.po` / `.mo` | 211/211 |
| `locales/pt_BR.po` / `.mo` | 211/211 |

`locales/ticketclock.pot` is the extracted template; the `.mo` files are the compiled
binaries GLPI loads.

**Both `.po` and `.mo` are committed.** There is no build step when a plugin is installed —
GLPI reads the `.mo` straight from `locales/` — so a repository without compiled catalogues
ships an untranslated plugin. The official `pluginsGLPI/example` does the same.

## How GLPI picks a catalogue

`Plugin::loadLang()` looks in `plugins/ticketclock/locales/` for a file named after the
language code, exactly as GLPI names its own: `en_GB.mo`, `fr_FR.mo`, `pt_BR.mo`,
`es_ES.mo`… The order is:

1. the **user's** language,
2. otherwise the **instance's default** language,
3. otherwise **`en_GB.mo`**,
4. otherwise no catalogue at all, and gettext falls back to the `msgid` — which is English,
   because that is what the source strings are.

> **Step 2 surprises people.** A Spanish user on an instance whose default language is
> Brazilian Portuguese sees TicketFlow in **Portuguese**, not English, because `es_ES.mo`
> does not exist and the instance default is tried before `en_GB`. This is GLPI core
> behaviour, identical for every plugin — verified against GLPI 11.0.4. The only cure is to
> ship the missing language.

GLPI 11.0.4 offers 64 languages. Shipping three means most users fall through to step 2
or 3.

There is also `GLPI_LOCAL_I18N_DIR`, where an installation can override or extend a plugin's
catalogue without touching the plugin. Useful for a customer who wants different wording;
mention it before anybody forks the plugin to change one sentence.

## Rules the code follows

* **English is the source language.** Every `__()` argument is English, and the catalogue is
  keyed on it. A translated string is never a key.
* **Every user-facing string goes through the `ticketclock` domain** — `__('…', 'ticketclock')`,
  `_n('…', '…', $n, 'ticketclock')`. The domain must match the plugin directory name.
* **No string concatenation for sentences.** Anything with a variable uses `sprintf` with
  positional placeholders (`%1$s`, `%2$s`), so translators can reorder them — French and
  Portuguese both need a different word order than English in several of these.
* **Plurals use `_n()`**, never `$n > 1 ? 'items' : 'item'`. Plural rules differ per
  language and the `.po` header declares them.
* **Nothing user-facing is hardcoded in a template.** Twig calls the same functions.

## Workflow

```bash
php tools/extract-locales.php     # sources        -> locales/ticketclock.pot
php tools/init-locale.php fr_FR   # .pot + existing -> locales/fr_FR.po (keeps translations)
#   ... translate the empty msgstr entries ...
php tools/compile-locales.php     # *.po           -> *.mo
```

All three are plain PHP with no dependencies:

* `extract-locales.php` scans **PHP and Twig** for the `ticketclock` domain. `xgettext` does
  not understand Twig, and half of the strings live in templates.
* `init-locale.php` creates or refreshes a catalogue. Existing translations survive, new
  strings arrive empty. `--identity` fills every entry with the source text, which is how
  `en_GB` is produced.
* `compile-locales.php` writes the binary `.mo`. `msgfmt` from gettext does the same job and
  is preferred when installed; this exists so a build never depends on a system package.

Run all three after touching any user-facing string. The extractor is the source of truth —
if a string does not appear in the `.pot`, it is not translatable, and that is a bug.

## Adding a language

1. `php tools/init-locale.php <code>` with GLPI's own code (`es_ES`, `de_DE`, `it_IT`…).
2. Translate the empty entries. Keep `%1$s`-style placeholders and `{{placeholder}}` tokens
   exactly as they are — the latter are TicketFlow's message placeholders, not text.
3. `php tools/compile-locales.php`.
4. Add `<lang>code</lang>` to `ticketclock.xml`, so the catalog lists what actually ships.
5. Commit both the `.po` and the `.mo`.

Completeness check:

```bash
php -r '$p=file_get_contents("locales/ticketclock.pot");
preg_match_all("/^msgid \"(.*)\"$/m",$p,$m);
$t=count(array_filter($m[1],fn($s)=>$s!==""));
foreach(glob("locales/*.po") as $f){$c=file_get_contents($f);
preg_match_all("/^msgstr(?:\[0\])? \"(.*)\"$/m",$c,$x);
printf("%-8s %d/%d\n",basename($f,".po"),count(array_filter($x[1],fn($s)=>$s!=="")),$t);}'
```

## A note on the catalog manifest

`ticketclock.xml` carries two different language concepts, and mixing them up is easy:

* `<langs>` lists the languages the **plugin interface** is available in. It must match the
  `.mo` files that ship — claiming a language nobody translated is worse than claiming none.
* `<description><short>` and `<long>` are the **catalog listing** text, in whatever languages
  you can write it. English, French and Brazilian Portuguese here.

## What is deliberately not done

**No Transifex or Weblate integration.** Larger GLPI plugins host translations on a platform
so contributors do not have to open pull requests. That is worth doing once there are
translators; wiring it up before then adds a service to maintain and nothing else. Until
then, a pull request with a `.po` and its `.mo` is the whole process.
